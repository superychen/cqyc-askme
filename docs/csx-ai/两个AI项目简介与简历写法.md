# 两个 AI 项目简介与简历写法

> 对应方案：《CSX-RAG与多Agent业务建设方案.md》。截至 2026-10-23，本次完成业务调研与方案设计，尚未实现这两个完整 AI 项目。原 Java 系统已存在的业务能力与新项目拟开发能力必须分开表述。

## 1. 项目一：CSX 供应商合作准入 RAG 助手

### 1.1 项目定位

面向潜在供应商及已注册供应商，将企业介绍、合作指南、注册说明和食安材料要求组织为可追溯知识服务，通过对话收集供货区域、经营品类与企业能力，辅助生成合作意向和注册资料草稿，再接入原供应商协同流程完成办理。

业务特色：供应商咨询不是孤立 FAQ，而是连接“了解公司—判断合作路径—准备材料—形成草稿—身份验证—受理及补正”的完整旅程。

### 1.2 当前可用的项目简介（方案设计阶段）

**项目名称：CSX 供应商合作准入 RAG 助手（方案设计/建设中）**

基于供应商协同、采购、主数据及食安系统业务，设计面向供应商的企业知识问答与合作准入助手。规划采用混合检索、重排、版本化引用和租户/供应商权限过滤，支持公司知识咨询、合作路径解释、材料清单及多轮资料草稿；通过安全表单和业务工具接入合作意向与注册流程，保留企业核验、原系统审批及账号升级机制。

可列出的本次工作：

- 梳理已有编码注册、无编码自助注册、合作意向和正式准入的业务差异，明确 RAG、工具调用及原系统审批边界。
- 设计公开知识、供应商私有资料及内部运营知识的隔离方案，覆盖检索、引用、附件和缓存权限。
- 设计语义分块、关键词/向量融合、重排、出处引用、文档版本和证据不足处理。
- 设计多轮草稿、安全验证、确认提交及受理状态查询，明确密码和验证码不进入模型上下文。

当前 `cqyc-askme` 可描述为已有文档导入代码基础，不能写成已完成企业检索问答或已联调供应商注册。

### 1.3 完成实现后可采用的简介模板

> 仅在对应能力实现并验证后使用，删除未完成项。

**项目简介：** 面向供应商咨询与合作准入场景，构建企业 RAG 助手，接入公司介绍、合作指南、注册及证件材料文档，通过混合检索、重排与引用生成提供可追溯回答，并结合多轮资料收集与工具调用辅助办理合作意向和注册申请。

**个人职责模板：**

- 负责文档解析、结构分块、图片辅助说明和知识版本管理，保留标题、页码/行号及适用范围，实现资料更新与撤回。
- 实现关键词与向量双路召回、融合及重排，处理供应商术语、精确编码、地区条件与无答案问题，输出可核对引用。
- 实现租户、供应商及子账号权限校验，将范围过滤贯穿检索、父文档扩展、附件、缓存和会话恢复。
- 实现意向资料槽位收集、草稿版本确认、安全表单和办理状态查询，对接原系统校验与受理流程。

**技术栈候选：** Python、FastAPI、LangGraph、BGE-M3、Milvus、关键词检索、重排模型、MinerU、Redis、MinIO、Vue 3、Java 业务适配。最终只写实际用到的组件。

### 1.4 可量化成果的填写方式

| 待填写项 | 记录方法 | 禁止替代方式 |
|---|---|---|
| 知识规模 | 已审核文档数、有效版本数、块数 | 扫描到的源码数量不等于对外知识规模 |
| 检索质量 | 固定业务标注集的 Recall@K/MRR | 不用一次成功问答代表准确率 |
| 回答质量 | 人工核对事实与引用支持率 | 不用模型自评分直接证明业务正确 |
| 办理效率 | 同任务人工基线与辅助流程耗时 | 不编造“效率提升 80%” |
| 响应与成本 | 固定环境下 P50/P95、平均单问成本 | 不拿单次最快耗时作系统指标 |

## 2. 项目二：CSX 采购与合规多 Agent 协同平台

### 2.1 项目定位

面向采购人员，以自然语言需求为入口，协调采购、主数据、食安、合同 Agent，完成商品与供应商核对、有效价格比较、证件缺口分析、合同要素审阅、采购草案及受控执行，支持跨系统任务状态和异常追踪。

业务特色：将商品治理、供应商区域状态、价格来源、证件满足和合同有效性统一到采购方案中；不是给每个系统加一个聊天框。

### 2.2 当前可用的项目简介（方案设计阶段）

**项目名称：CSX 采购与合规多 Agent 协同平台（方案设计/建设中）**

基于 SCM、新旧主数据、供应商协同和 FQS 系统，设计由任务协调器与采购、主数据、食安、合同 Agent 组成的业务协同平台。通过标准工具网关复用既有采购规则、申请审批、证件核验和电子合同能力，规划实现需求拆解、跨域核对、采购方案比较、人工确认及业务审批、订单执行与履约异常追踪，并设计任务持久化、交易幂等及部分成功处理。

可列出的本次工作：

- 阅读重点系统业务说明与关键源码，整理领域职责、真实能力锚点、工具清单及集成缺口。
- 设计 Supervisor + 领域子流程，明确主数据依赖、证件/合同并行核对、冲突收口和有限执行预算。
- 设计基于业务硬约束的成本比较，保留税价、单位、运费、交期和报价有效期口径。
- 设计确认与审批分离、检查点与交易幂等分离、超时未知结果核对及回调版本隔离机制。
- 复用 FQS 已有多模态证件核验定位，避免把原系统 AI 调用和自动竞价程序写成新项目研发成果。

**项目简介：** 围绕企业采购下单与合规校验，构建 Supervisor 协调的多 Agent 平台，将采购、主数据、食安和合同能力通过工具网关接入统一工作流，实现自然语言需求解析、跨域资料校验、采购成本比较、合同差异审阅、受控下单与异常追踪。

**个人职责模板：**

- 基于 LangGraph 设计领域子图与依赖路由，组织主数据先行、证件/合同并行核对及采购方案汇总，支持人工输入、审批等待与任务恢复。
- 封装 Java 业务适配工具，统一结构化参数、可信身份、错误分类及业务回执，复用原 SCM 创建规则与 MDM/FQS 应用服务。

**技术栈候选：** Python、LangGraph、FastAPI、Pydantic、Java/Spring Boot 网关、REST/Feign/Dubbo、关系数据库检查点/账本、Redis、RocketMQ、RAG 与多模态模型。最终按真实实现删减。

## 3. 两个项目如何避免重复

| 维度 | RAG 项目 | 多 Agent 项目 |
|---|---|---|
| 业务主线 | 供应商了解公司与合作准入 | 内部采购决策与跨域执行 |
| 主要难点 | 知识质量、版本、权限、引用和多轮收集 | 任务依赖、工具权限、业务规则、审批和恢复 |
| 检索角色 | 主能力 | 获取制度/合同依据的共享服务 |
| 工具角色 | 状态查询与意向/注册办理 | 跨系统查询、预检和业务执行 |
| 演示产物 | 有出处的回答、资料草稿、受理回执 | 成本方案、证件/合同证据、执行与恢复轨迹 |
| 指标 | 检索/引用、材料完整度、办理耗时 | 任务完成、重复写入、恢复、业务处理耗时 |

## 4. 面试中应讲清的设计取舍

1. **为什么不只做 RAG？** 静态文档不能证明此时的供应商可用、订单已创建或证件已满足，必须查询权威业务接口。
2. **为什么拆领域 Agent？** 采购、主数据、食安、合同有独立规则、工具和证据边界；协调器处理依赖，规则引擎负责硬约束。
3. **为什么不用 Agent 直接改数据库？** 原系统承担权限、审批、事务和事件一致性，直接写表会绕过这些机制。
4. **为什么检查点不能解决重复下单？** 检查点保存编排状态，外部业务可能在确认丢失前已提交；需业务请求号、原子映射与查单能力。
5. **如何处理低价但不合规？** 先筛出满足交期/主体/证件/合同要求的候选，再由程序比较同口径成本。
6. **如何避免跨供应商泄漏？** 从可信身份生成范围，贯穿召回、引用、附件、缓存、工具和恢复，不靠 prompt 保密。
7. **食安能力哪些是自己做的？** 如实说明原 FQS 已有识别核验，自己的新增工作是工具适配、任务编排、版本隔离和结果解释。
8. **如何证明效果？** 用业务标注、固定评测口径、执行日志、回执与人工基线；没有数据就不填百分比。
